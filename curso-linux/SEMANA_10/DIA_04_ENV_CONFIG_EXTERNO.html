Configuração Externa: Segredo Fora do Script

segredo não mora em script, histórico ou repositório — fica separado, protegido e documentado

1. O chamado

Seu backup.sh tem mysqldump -u root -pSENHA_AQUI app > backup.sql direto no código. Um colega pergunta: "outro usuário do sistema pode ver isso?" — e a resposta é sim, ps aux mostra a senha em texto plano pra qualquer um olhando os processos rodando.

2. O sênior te conta

Semana passada, outro ticket Um admin júnior escreveu um backup.sh pra dump de banco, testou local, funcionou, subiu pra produção agendado no cron. Semanas depois, uma auditoria de segurança rodou ps aux num momento em que o backup estava executando — e a senha do banco apareceu em texto plano na tela, visível pra qualquer usuário logado no servidor naquele instante. Ninguém tinha explorado isso ainda, mas o relatório da auditoria classificou como credencial exposta em produção, mesmo sem incidente real. A correção não foi trocar a senha — foi tirar ela do comando por completo, movendo pra um arquivo protegido que só o dono consegue ler. O ponto que fica: um risco não precisa ser explorado pra contar como falha — só precisa estar visível pra quem não deveria ver.

4. Ferramentas e leitura da evidência

ComandoO que observar e por que importa
ps aux | grep mysqldumpConfirma se a senha está visível na linha de comando de um processo rodando.
chmod 600 /etc/backup/mysql_creds.cnfRestringe o arquivo de credenciais só ao dono, protegendo contra leitura por outros usuários.
mysqldump --defaults-extra-file=arquivo.cnfLê a credencial do arquivo protegido, sem expor nada na linha de comando.
$ ps aux | grep mysqldump
root  2731  mysqldump -u root -pSENHA_AQUI app > backup.sql

--- corrigido ---
$ cat /etc/backup/mysql_creds.cnf
[client]
user=backup
password=SENHA_AQUI
host=localhost
$ chmod 600 /etc/backup/mysql_creds.cnf
$ ls -l /etc/backup/mysql_creds.cnf
-rw------- 1 root root 76 /etc/backup/mysql_creds.cnf

$ ./backup.sh   # script agora usa --defaults-extra-file
Backup completed successfully

5. Laboratório guiado — marca conforme for testando

🖥️ Testar este laboratório agora, num terminal Linux real (Killercoda) →
Segurança: execute os testes apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. Ação: reproduza o risco — escreva um script de teste que recebe uma senha fictícia como argumento e imprime "conectando com senha $1", rode em background.
    $ cat > teste_senha.sh <<'EOF' #!/bin/bash echo "conectando com senha $1" sleep 30 EOF $ chmod +x teste_senha.sh $ ./teste_senha.sh SENHA_FICTICIA_123 & $ ps aux | grep teste_senha usr 8821 ./teste_senha.sh SENHA_FICTICIA_123
    Resultado esperado: senha fictícia visível na saída do ps aux, reproduzindo o risco.
    Por quê: qualquer processo em execução expõe seus argumentos completos pra qualquer usuário do sistema — isso é comportamento normal do kernel, não um bug.
  2. Ação: crie um arquivo de configuração separado com a credencial fictícia e proteja com chmod 600.
    $ cat > /tmp/teste_creds.cnf <<'EOF' [client] user=backup password=SENHA_FICTICIA_123 EOF $ chmod 600 /tmp/teste_creds.cnf $ ls -l /tmp/teste_creds.cnf -rw------- 1 usr usr 48 /tmp/teste_creds.cnf
    Resultado esperado: -rw------- confirmado, só o dono com acesso ao arquivo.
    Por quê: mover a credencial pra um arquivo sozinho não protege nada — sem chmod 600, qualquer usuário ainda pode ler o conteúdo diretamente.
    🧑‍🏫 Aqui entra o Mentor (em breve): se uma ferramenta específica não tiver opção de arquivo de credenciais, este é o ponto onde o chat com o Sênior-IA vai ajudar a encontrar uma alternativa segura.
  3. Ação: adapte o script de teste pra ler do arquivo de configuração em vez de receber a senha como argumento, e confirme com ps aux que ela não aparece mais.
    $ cat > teste_senha2.sh <<'EOF' #!/bin/bash source /tmp/teste_creds.cnf 2>/dev/null || . <(grep = /tmp/teste_creds.cnf) echo "conectando ao banco (senha lida de arquivo protegido)" sleep 30 EOF $ chmod +x teste_senha2.sh $ ./teste_senha2.sh & $ ps aux | grep teste_senha2 usr 8830 ./teste_senha2.sh
    Resultado esperado: ps aux não mostra mais a senha na linha de comando — só o nome do script.
    Cilada comum: esquecer de aplicar chmod 600 no arquivo novo, achando que só "separar" já resolveu — sem a permissão restrita, o risco continua, só mudou de lugar.
  4. Ação: simule o cenário de "senha já commitada" — confirme que remover do arquivo atual não apaga o histórico do git.
    $ git init teste-repo && cd teste-repo $ echo 'senha=SENHA_ANTIGA_123' > config.txt && git add . && git commit -m "add config" $ echo 'senha=REMOVIDA' > config.txt && git add . && git commit -m "remove senha do arquivo atual" $ git log -p --all | grep SENHA_ANTIGA_123 +senha=SENHA_ANTIGA_123
    Resultado esperado: a senha antiga aparece no histórico do git mesmo depois de removida da versão atual.
    Por quê: git guarda cada commit como um snapshot — remover de uma versão nova não apaga o registro das versões anteriores, sempre acessíveis via histórico.
  5. Ação: documente: risco original, correção aplicada, validação de que a senha não está mais exposta.
    Resultado esperado: registro completo reproduzindo o painel 6 da prancha de hoje.

6. Antes de ver as opções — tenta responder

🧠 Recall ativo: por que uma senha na linha de comando (-pSENHA) é visível pra outros usuários do sistema, mesmo sem eles terem acesso ao arquivo do script?
Comandos rodando aparecem com seus argumentos completos em ps aux — qualquer usuário do sistema pode ver a linha de comando completa de qualquer processo, incluindo senhas passadas como argumento. Um arquivo de configuração protegido evita essa exposição.

7. Questão comentada — clica numa alternativa

Sua senha do banco está direto no comando mysqldump dentro do script. Qual é a correção correta pra proteger essa credencial?
💡 Analogia do Sênior para Fixar: Separar a configuração (.env ou config.conf) do código do script é como trocar o chip da operadora sem comprar um celular novo: você muda senhas e IPs sem mexer na lógica.
QUESTÃO 2 de 3 — cenário de erro real

7.1 git diff mostra a senha antiga sendo removida do script — isso já resolve o vazamento por completo?

O git diff confirma que a linha com -pSENHA_AQUI foi removida do backup.sh na versão nova do script.

Remover a senha da versão atual do script já garante que ela não está mais exposta em lugar nenhum?
💡 Analogia do Sênior para Fixar: O comando 'source /etc/default/meuservico' carrega os parâmetros externos como variáveis nativas: mantém credenciais e caminhos organizados em um único arquivo de texto.
QUESTÃO 3 de 3 — detalhe que confunde todo iniciante

7.2 "Se o arquivo de credenciais está fora do script, chmod 600 nele é só uma formalidade opcional?"

Um colega cria o arquivo de credenciais separado, mas não aplica chmod 600, deixando com a permissão padrão (legível por outros usuários).

Isso ainda representa um risco de segurança?
💡 Analogia do Sênior para Fixar: Proteger o arquivo .env com permissão 600 (chmod 600) é colocar o cofre de senhas em gaveta trancada: impede que usuários comuns vejam credenciais de banco de dados.

8. Procedimento profissional

  1. Nunca escreva credenciais direto no código de um script.
  2. Crie um arquivo de configuração separado, fora do repositório de código quando possível.
  3. Proteja o arquivo com chmod 600, restrito só ao dono.
  4. Use a opção da ferramenta que lê credenciais de arquivo (--defaults-extra-file, etc), nunca argumento de linha de comando.
  5. Se a senha já foi commitada, trate como comprometida — troque-a, não confie só em removê-la do código.

Prevenção

Padronize um template de script novo que já parte com a leitura de credenciais via arquivo externo protegido (--defaults-extra-file ou source de um .env com chmod 600) — assim ninguém precisa lembrar de aplicar a correção depois, porque o script já nasce sem a senha visível em lugar nenhum.

9. Validação e encerramento

  • Nenhuma credencial está escrita direto no código do script.
  • O arquivo de configuração separado está protegido com chmod 600.
  • ps aux confirma que a senha não aparece mais na linha de comando.
  • Se a senha já tinha sido exposta antes, ela foi tratada como comprometida (trocada).

Rollback e limites

Separar credenciais e restringir permissão não são mudanças destrutivas — não existe rollback necessário. O risco real irreversível é uma senha já exposta em histórico de git ou log — a única correção real nesse caso é trocar a credencial.

10. Resposta final

Alternativa correta: B. Nesta aula, a decisão correta foi mover a credencial pra um arquivo de configuração separado, protegido com chmod 600, referenciado via --defaults-extra-file. O ponto central do caso é este: segredo não mora em script, histórico ou repositório — fica separado, protegido e documentado.
