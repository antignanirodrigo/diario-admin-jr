Cron e PATH: Tarefa Agendada Sem Log é Chute

cron exige caminho claro, saída registrada e validação depois

ANTES DE ALTERAR, OBSERVE. DEPOIS DE ALTERAR, VALIDE.

1. O chamado

2. O sênior te conta

Quarta-feira, Semana 10 Ontem você aprendeu que um healthcheck não pode confiar só no último resultado. Hoje a pegadinha é parecida em espírito, mas muda de terreno: o mesmo script que funciona perfeitamente quando você testa manualmente pode falhar sozinho, de madrugada, sem ninguém olhando.

Testei um backup.sh na mão, rodando rsync pra sincronizar dados. Funcionou liso. Agendei no crontab pra rodar às 2h da manhã, satisfeito. No dia seguinte, ticket na fila: "backup agendado falhou, nenhum backup gerado" — o mesmo script que "funcionou no teste" simplesmente não rodou. Fui direto no log e vi a explicação: rsync: command not found, saída 127.

O rsync estava lá, instalado, funcionando — eu tinha acabado de usá-lo no teste manual. O problema era que o cron não herda o mesmo PATH completo do meu shell interativo. O ambiente do cron é mínimo, geralmente só /usr/bin:/bin — e o rsync estava numa pasta (/usr/local/bin) que não fazia parte dessa lista curta. Meu teste manual "provava" que o script funcionava, mas provava isso num ambiente diferente do que o cron realmente usa pra executar.

A correção é declarar PATH explicitamente logo no topo do script — ou usar caminhos absolutos pros comandos críticos — pra nunca depender do ambiente de quem (ou o quê) está chamando o script. E sempre redirecionar toda a saída pra um log: sem ele, uma tarefa agendada que falha de madrugada é praticamente invisível até alguém sentir falta do resultado. Hoje você pratica exatamente essa disciplina: nunca confiar que "funcionou no teste manual" significa "vai funcionar agendado".

4. Ferramentas e leitura da evidência

ElementoO que observar e por que importa
tail -n 20 /var/log/backup_cron.logO log é a única evidência do que aconteceu numa execução agendada — sem ele, é chute.
PATH=... no topo do scriptDeclara explicitamente onde procurar comandos, independente do ambiente que chamou o script.
0 2 * * * /caminho/script.sh >> /log 2>&1Linha do crontab, sempre com saída (normal e erro) redirecionada pra um log.
$ tail -n 20 /var/log/backup_cron.log
/bin/sh: rsync: command not found
saída 127

--- corrigido ---
#!/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
set -euo pipefail
/usr/bin/rsync -a /dados/ /backup/dados/

$ crontab -e
0 2 * * * /home/adminjr/backup.sh >> /var/log/backup_cron.log 2>&1

5. Laboratório guiado — pegue na mão, comando por comando

🖥️ Testar este laboratório agora, num terminal Linux real (Killercoda) →
Segurança: execute os testes apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. Ação: compare o PATH do seu shell interativo com o PATH que o cron realmente usa.
    $ echo $PATH $ (crontab -l 2>/dev/null; echo "* * * * * echo \$PATH > /tmp/cronpath.txt") | crontab - $ sleep 65 && cat /tmp/cronpath.txt
    Resultado esperado: os dois PATHs claramente diferentes — o do cron bem mais curto que o do shell interativo.
    Por que fizemos isso: ver essa diferença com os próprios olhos, no seu próprio sistema, é o que torna concreto o que causou o incidente da história — não é teoria, é o ambiente real do cron.
    Cilada comum: esquecer de remover essa linha de teste do crontab depois — ela roda a cada minuto indefinidamente se não for removida.
  2. Ação: remova a linha de teste, escreva um script que usa um comando fora do PATH mínimo do cron, e confirme que ele falha quando agendado.
    $ crontab -l | grep -v cronpath | crontab - $ cat > teste.sh << 'EOF' #!/bin/bash rsync --version EOF $ chmod +x teste.sh $ (crontab -l 2>/dev/null; echo "* * * * * $HOME/teste.sh >> /tmp/teste.log 2>&1") | crontab - $ sleep 65 && cat /tmp/teste.log
    Resultado esperado: "command not found" no log — reproduzindo exatamente o sintoma da história, mesmo com rsync funcionando perfeitamente no terminal.
    Por que fizemos isso: sentir esse "funciona no terminal, falha no cron" na prática é o que fixa a lição — não é intuitivo até você ver acontecer.
    Cilada comum: testar só manualmente e nunca confirmar a execução agendada real — foi exatamente esse pulo que causou o ticket na história.
  3. Ação: adicione PATH explícito no início do script e teste de novo.
    $ cat > teste.sh << 'EOF' #!/bin/bash PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin rsync --version EOF $ sleep 65 && cat /tmp/teste.log
    Resultado esperado: execução agendada bem-sucedida — a saída da versão do rsync aparece no log, comando encontrado.
    Por que fizemos isso: essa é a correção exata que resolveu o ticket da história — declarar PATH explicitamente resolve o problema na raiz, não importa quem chame o script depois.
    Cilada comum: copiar um PATH genérico da internet sem confirmar se ele realmente cobre onde os comandos do SEU sistema estão instalados.
    🧑‍🏫 Aqui entra o Mentor (em breve): se uma tarefa agendada continuar falhando mesmo com PATH declarado, este é o ponto onde o chat com o Sênior-IA vai ajudar a investigar outras diferenças de ambiente.
  4. Ação: confirme que o redirecionamento completo captura tudo, inclusive erros, removendo a tarefa de teste ao final.
    $ crontab -l | grep -v teste.sh | crontab - $ cat /tmp/teste.log
    Resultado esperado: log completo com a saída real da execução, tarefa de teste removida do crontab pra não continuar rodando.
    Por que fizemos isso: o log é a única evidência de uma execução agendada — sem ele, você está adivinhando o que aconteceu de madrugada, sem ninguém olhando.
    Cilada comum: esquecer de limpar as tarefas de teste do crontab — elas continuam consumindo recursos e gerando log indefinidamente.
  5. Ação: documente PATH do shell vs. PATH do cron, correção aplicada, validação da execução agendada.
    # anote no seu diário de bordo: PATH shell: /usr/local/bin:/usr/bin:/bin:... PATH cron: /usr/bin:/bin (bem mais curto) Correção: PATH explícito declarado no topo do script Validado: execução agendada real confirmada, não só teste manual
    Resultado esperado: registro completo reproduzindo o painel 6 da prancha de hoje.
    Por que fizemos isso: documentar os dois PATHs lado a lado é o que prova, pra qualquer revisão futura, exatamente qual era a diferença e por que a correção funciona.
    Cilada comum: documentar só "corrigido", sem registrar os dois PATHs comparados — sem esse contraste, fica difícil explicar a causa raiz pra outra pessoa.

6. Antes de ver as opções — tenta responder

🧠 Recall ativo: por que um script que funciona manualmente pode falhar quando rodado pelo cron?
O cron não carrega o mesmo PATH completo do seu shell interativo — o PATH do cron é bem mais curto (geralmente só /usr/bin:/bin), então comandos em pastas fora dessa lista (como rsync em /usr/local/bin) simplesmente não são encontrados.

8. Procedimento profissional

  1. Sempre declare PATH explicitamente no início de scripts que serão agendados.
  2. Use caminhos absolutos para comandos críticos quando possível.
  3. Redirecione toda a saída (normal e erro) pra um log com 2>&1.
  4. Agende com set -euo pipefail no script, pra falhar visivelmente em erro.
  5. Valide a execução agendada de verdade, não só o teste manual.

Prevenção

Crie um template padrão de script agendável, já com PATH explícito e set -euo pipefail no topo, e copie dele sempre que um script novo for destinado ao cron. Isso remove a possibilidade de esquecer essa declaração, o mesmo esquecimento que gerou o ticket #8421 da história.

9. Validação e encerramento

  • PATH foi declarado explicitamente no script, não confiado no ambiente do cron.
  • Toda a saída da execução agendada é registrada em log.
  • O script foi validado rodando de verdade pelo cron, não só manualmente.
  • A causa raiz (diferença de ambiente) foi corretamente identificada e documentada.

Rollback e limites

Declarar PATH e redirecionar log não são mudanças destrutivas — não existe rollback necessário. O risco real evitado é justamente NÃO ter essas proteções, deixando um backup crítico falhando silenciosamente todas as noites.

10. Resposta final

Alternativa correta: B. Nesta aula, a decisão correta foi declarar PATH explicitamente no início do script (ou usar caminho absoluto), já que o cron usa um PATH mínimo diferente do shell interativo. O ponto central do caso é este: tarefa agendada sem log é chute — cron exige caminho claro, saída registrada e validação depois.
