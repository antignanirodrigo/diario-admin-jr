Backup Automatizado: tar + rsync com Verificação

backup só é sucesso quando cada etapa confirma que terminou bem

ANTES DE ALTERAR, OBSERVE. DEPOIS DE ALTERAR, VALIDE.

1. O chamado

Seu script de backup roda tar -czf seguido de rsync e depois echo "Backup concluído" — sem checar nada no meio. "Rodou sem gritar" não é a mesma coisa que "funcionou de verdade": o tar pode ter falhado por disco cheio, e o script nunca saberia.

2. O sênior te conta

Segunda-feira, abrindo a Semana 10 A Semana 9 te deu um toolkit completo de bash: shebang, condicionais, loops, funções, set -e. Hoje esse toolkit vira scripts de verdade, prontos pra rodar sem supervisão em produção — começando pelo mais clássico de todos: backup.

O chamado que me marcou nesse assunto foi um script de backup que "sempre funcionava". Rodava tar -czf, depois rsync, e no final um echo "Backup concluído". Nenhum erro na tela, nunca. Achei que estava tudo certo até o dia em que precisei restaurar de verdade — e o arquivo .tar.gz estava corrompido, cortado no meio. O disco tinha ficado cheio durante a compactação, semanas antes, e o tar escreveu só uma parte do arquivo. O script não percebeu, o rsync enviou o arquivo parcial do mesmo jeito, e o echo final disse "concluído" com a maior tranquilidade — porque nenhum desses comandos tinha travado o script, só produzido um resultado ruim silenciosamente.

A lição que aprendi ali é simples de dizer e fácil de esquecer: "rodou sem gritar" não é a mesma coisa que "funcionou de verdade". Um comando pode falhar PARCIALMENTE sem interromper o script inteiro. A correção não é complicada — encadear cada etapa crítica com || ("se isso falhar, registre o erro e saia"), e só declarar sucesso no log depois que TODAS as etapas realmente passaram, uma por uma, com evidência própria.

Hoje você escreve exatamente esse script: tar verificado, rsync verificado, e um log que conta a história real de cada etapa — não um "concluído" genérico que pode estar mentindo.

app.tgz
$ echo "Backup concluído"
Backup concluído   # arquivo parcial enviado!

--- com verificação de cada etapa ---
$ tar -czf "$ARQ" "$ORIGEM" || { echo "ERRO no tar" >> "$LOG"; exit 1; }
$ rsync "$ARQ" backup:/srv/backup/ || exit 1

5. Laboratório guiado — pegue na mão, comando por comando

Segurança: execute os testes apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. Ação: escreva um script de backup simples com tar, sem nenhuma verificação de erro ainda.
    $ mkdir -p ~/lab_backup/origem && touch ~/lab_backup/origem/arquivo.txt $ cat > backup.sh << 'EOF' #!/bin/bash tar -czf backup.tgz ~/lab_backup/origem echo "Backup concluído" EOF $ chmod +x backup.sh && ./backup.sh
    Resultado esperado: script funcional no caminho feliz, sem tratamento de erro — sempre imprime "Backup concluído", mesmo que algo falhe.
    Por que fizemos isso: ver a versão ingênua funcionando é o ponto de partida — ela "funciona" no caso normal, exatamente como o script da história antes de eu descobrir o problema.
    Cilada comum: testar só esse caminho feliz e nunca simular uma falha — é exatamente esse ponto cego que causou o backup corrompido da história.
  2. Ação: adicione || com registro de erro e exit 1 depois do tar.
    $ cat > backup.sh << 'EOF' #!/bin/bash LOG=~/lab_backup/backup.log tar -czf backup.tgz ~/lab_backup/origem || { echo "ERRO no tar" >> "$LOG"; exit 1; } echo "TAR OK" >> "$LOG" EOF $ chmod +x backup.sh
    Resultado esperado: script preparado pra parar e registrar erro se o tar falhar, em vez de seguir cegamente.
    Por que fizemos isso: esse é o encadeamento exato que teria evitado o backup corrompido da história — parar e registrar no primeiro sinal de falha real.
    Cilada comum: esquecer o exit 1 depois do echo de erro — sem ele, o script registra o erro no log mas continua rodando de qualquer jeito.
  3. Ação: simule uma falha apontando o tar pra uma origem que não existe, e confirme que o script para com a mensagem correta.
    $ sed -i 's#~/lab_backup/origem#/caminho/que/nao/existe#' backup.sh $ ./backup.sh; echo "exit code: $?" $ cat ~/lab_backup/backup.log
    Resultado esperado: "ERRO no tar" no log, exit code diferente de zero, script encerrado antes de qualquer outra etapa.
    Por que fizemos isso: forçar a falha de propósito é o único jeito de confirmar que a proteção realmente funciona — sem testar o caminho de erro, você só está confiando na intenção do código, não no comportamento real.
    Cilada comum: nunca testar deliberadamente o caminho de falha — é exatamente esse teste que faltou no script original da história.
    🧑‍🏫 Aqui entra o Mentor (em breve): se o script não parar como esperado numa falha simulada, este é o ponto onde o chat com o Sênior-IA vai ajudar a revisar a lógica de encadeamento.
  4. Ação: corrija a simulação e confirme que o script completa com sucesso, registrando cada etapa no log.
    $ sed -i 's#/caminho/que/nao/existe#~/lab_backup/origem#' backup.sh $ ./backup.sh $ cat ~/lab_backup/backup.log
    Resultado esperado: log completo mostrando "TAR OK", confirmando que a etapa passou de verdade, não só que o script terminou.
    Por que fizemos isso: ver o log registrar sucesso real (não genérico) é o que a Questão 2 vai testar — a diferença entre "rodou até o fim" e "cada etapa confirmou que funcionou".
    Cilada comum: confiar só na ausência de mensagem de erro na tela — sempre confira o conteúdo real do log antes de considerar o backup validado.
  5. Ação: documente cenário de falha testado, cenário de sucesso testado, conteúdo do log final.
    # anote no seu diário de bordo: Falha simulada: origem inexistente -> "ERRO no tar" no log, exit 1, script parou Sucesso: origem válida -> "TAR OK" no log, script completou Log final conferido linha por linha, não só ausência de erro na tela
    Resultado esperado: registro completo reproduzindo o painel 6 da prancha de hoje.
    Por que fizemos isso: documentar os dois cenários (falha e sucesso) é a prova de que o script foi testado de verdade nos dois caminhos, não só no que "sempre funciona".
    Cilada comum: documentar só o cenário de sucesso — sem o teste de falha registrado, ninguém sabe se a proteção contra erro realmente foi validada.

7. Questão comentada — clica numa alternativa

Seu script de backup roda tar e rsync sem checar nenhum resultado no meio. Qual é a correção correta pra garantir que "sucesso" só seja declarado se as duas etapas realmente funcionarem?
💡 Analogia do Sênior para Fixar: O comando 'tar -czf backup.tar.gz' é a mala selada a vácuo com carimbo de data: compacta e congela os arquivos do sistema naquele minuto exato.
QUESTÃO 2 de 3 — cenário de erro real

7.1 Depois de corrigir o espaço em disco, o script roda e o log mostra TAR OK e RSYNC OK — isso confirma o quê?

O arquivo /var/log/backup.log agora mostra INICIO backup, TAR OK, RSYNC OK e BACKUP OK, todos com timestamps.

Qual é a leitura correta desse log completo?
💡 Analogia do Sênior para Fixar: Excluir pastas como /proc, /sys e /tmp do backup é como não embalar a água da torneira na mudança: são arquivos voláteis criados dinamicamente pela memória RAM.
QUESTÃO 3 de 3 — detalhe que confunde todo iniciante

7.2 "|| exit 1 e && exit 1 fazem a mesma coisa?"

Um colega troca rsync ... || exit 1 por rsync ... && exit 1 por engano, achando que os dois operadores são intercambiáveis.

Qual é a diferença real entre os dois?
💡 Analogia do Sênior para Fixar: Armazenar a soma SHA-256 do arquivo .tar.gz no cofre é o lacre de segurança: garante que o arquivo de backup não sofreu corrupção de disco durante o armazenamento.

8. Procedimento profissional

  1. Encadeie cada etapa crítica com || pra tratar falha imediatamente.
  2. Registre no log cada etapa individualmente (TAR OK, RSYNC OK), não só o resultado final.
  3. Só declare SUCCESS no log se todas as etapas realmente passaram.
  4. Teste deliberadamente com uma etapa falhando (disco cheio simulado), confirmando que o script para.
  5. Valide o log gerado, não confie só na ausência de erro na tela.

Prevenção

Adicione um healthcheck de espaço em disco ANTES de iniciar o tar (ex.: alertar se menos de 20% livre). Isso ataca a causa raiz da história — disco cheio — antes mesmo dela chegar a gerar um arquivo parcial, em vez de só detectar o problema depois que ele já aconteceu.

9. Validação e encerramento

  • Cada etapa crítica (tar, rsync) tem tratamento de erro explícito.
  • O log registra cada etapa individualmente, não só o resultado final.
  • SUCCESS só é registrado se todas as etapas realmente passaram.
  • O script foi testado deliberadamente com falha simulada, não só o caminho feliz.

Rollback e limites

Um script de backup com verificação não é destrutivo em si — mas se ele reportar sucesso falso (sem essa verificação), o dano real só aparece quando alguém tentar restaurar e descobrir que o backup está incompleto. É por isso que a verificação de cada etapa é tão importante.
