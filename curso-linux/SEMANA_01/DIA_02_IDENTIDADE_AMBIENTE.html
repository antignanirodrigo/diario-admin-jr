2. O sênior te conta

🧑‍🏫 antes dos termos técnicos, a história de hoje Hoje um colega perguntou pro Júnior, meio de brincadeira: "você tá como root aí?". E ele quase respondeu de cabeça — "acho que sim, tenho acesso a produção". Parei ele antes de terminar a frase: ter acesso e ser uma coisa não são o mesmo dado. Fizemos o teste junto: rodamos id e vimos que ele estava no grupo sudo, mas logado como usuário comum — aquilo que ele já tinha visto ontem, agora aparecendo de novo, num contexto diferente.

Mas fui além. Mostrei que "quem eu sou e onde estou" na verdade são quatro perguntas diferentes, não uma: quem está logado, que privilégio essa conta tem, em que máquina física ou virtual você está, e que sistema exatamente está rodando por baixo. Contei um caso real de um outro júnior, em outra empresa, que confundiu duas dessas perguntas: rodou uname -a, viu o número do kernel, e concluiu — errado — que aquilo dizia a distribuição Linux instalada. Aplicou um comando específico de uma distro, no lugar errado, achando que estava seguro.

Foi por isso que hoje, antes de qualquer diagnóstico de verdade, ensinei pro Júnior o hábito que você vai treinar agora: uma pergunta, um comando, sem achismo. Nunca misturar as quatro camadas.

4. Ferramentas e leitura da evidência

ComandoO que observar e por que importa
whoamiMostra só o nome da conta logada — a informação mais superficial das quatro.
idMostra UID, GID e todos os grupos — é aqui que você confirma privilégio de verdade.

$ hostnamectl

5. Laboratório guiado — pegue na mão, comando por comando

🖥️ Testar este laboratório agora, num terminal Linux real (Killercoda) →
Segurança: execute as mudanças apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. CENÁRIOAção: Crie um usuário de teste para comparar identidades lado a lado — é vendo a diferença que o conceito de UID/GID gruda.
    sudo useradd -m teste-jr id # a SUA identidade id teste-jr # a identidade dele groups teste-jr # em que grupos ele entrou
    🔍 Detalhar esse comando
    sudo
    Executa o comando com privilégios de root — criar um usuário é uma mudança de sistema, exige privilégio elevado.
    useradd
    Cria uma nova conta de usuário no sistema.
    -m
    Cria também a pasta pessoal (home) do novo usuário — sem essa flag, o usuário existe mas não tem pasta própria.
    teste-jr
    O nome da conta a ser criada.
    Resultado esperado: dois blocos com uid=, gid= e groups= claramente diferentes. Você provavelmente está em grupos como sudo ou adm; o teste-jr não está em nenhum deles.
    Por que fizemos isso: "Permission denied" quase nunca é sobre o comando — é sobre quem executou. Comparar duas identidades na mesma máquina mostra, em uma tela, por que o mesmo script tem dois destinos diferentes.
    Cilada comum: criar usuário em servidor de produção "só pra testar". Só em VM descartável — e anote o nome, você vai removê-lo no último passo.
    Se o seu resultado foi diferente
    "useradd: command not found" → use sudo adduser --disabled-password --gecos '' teste-jr (mais comum em Debian/Ubuntu).
    "id: teste-jr: no such user" → o useradd falhou silenciosamente. Rode de novo observando a saída, ou confirme com grep teste-jr /etc/passwd.
    Os UIDs são muito parecidos (ex: 1000 e 1001) → normal — o que importa não é o número, é a lista de grupos. É ali que mora a diferença de poder entre as duas contas.
  2. Ação: Rode, em sequência, os quatro comandos de identidade desta aula.
    whoami id hostnamectl uname -a
    🔍 Detalhar cada comando desse bloco
    whoami
    Mostra só o nome (login) do usuário da sessão atual.
    id
    Mostra UID, GID e a lista completa de grupos do usuário.
    hostnamectl
    Identifica hostname, sistema operacional, versão do kernel e arquitetura.
    uname -a
    Mostra informações do kernel (nome, hostname, versão, build, arquitetura) — não mostra a distribuição.
    Resultado esperado: quatro saídas diferentes, cada uma respondendo uma pergunta específica (quem, privilégio, onde, o quê).
    Por que fizemos isso: cada comando responde só UMA das quatro perguntas — misturar a leitura de um com a conclusão de outro é exatamente o erro que gera mal-entendido, como o "você tá como root?" do início da aula.
    Cilada comum: rodar só whoami e achar que já é suficiente. Ele mostra o nome da conta, não o privilégio — é a camada mais superficial das quatro.
  3. Ação: Na saída de id, identifique qual grupo daria a você poder de virar root com sudo.
    id
    🔍 Detalhar esse comando
    id
    Mostra UID (identificador numérico do usuário), GID (grupo primário) e a lista de todos os grupos secundários aos quais a conta pertence.
    Resultado esperado: o grupo sudo (ou wheel, em algumas distros) aparece listado, mas você continua logado como seu usuário normal.
    Por que fizemos isso: estar listado num grupo é autorização, não identidade ativa — sua sessão não muda de dono só por você pertencer ao grupo certo.
    Cilada comum: ver sudo na lista de grupos e responder "sim, sou root" pro colega. Pertencer ao grupo não é a mesma coisa que estar rodando como root agora.
  4. Ação: Rode cat /etc/os-release e compare com o que uname -a mostrou.
    cat /etc/os-release
    🔍 Detalhar esse comando
    cat
    Mostra o conteúdo de um arquivo de texto direto na tela, do início ao fim.
    /etc/os-release
    Arquivo padrão (systemd) com metadados da distribuição: nome, versão, ID e URL de suporte — é a fonte confiável para saber a distro, diferente do kernel.
    Resultado esperado: os-release mostra o nome da distribuição (ex: Ubuntu 22.04); uname -a não mostra isso, só o kernel.
    Por que fizemos isso: distribuições diferentes podem rodar exatamente a mesma versão de kernel — se você precisa saber a distro de verdade (pra escolher o comando certo de pacote, por exemplo), o kernel sozinho não serve.
    Cilada comum: concluir a distribuição só pelo número do kernel em uname -a — foi exatamente esse o erro do caso real que contei na história de hoje.
  5. Ação: Escreva, numa frase, a diferença entre "estar no grupo sudo" e "estar como root agora".
    # não é comando de shell — é registro escrito, uma frase só # ex: "Grupo sudo autoriza; root ativo é quando eu digito sudo antes de um comando."
    Resultado esperado: uma frase que outra pessoa entenderia sem precisar perguntar nada de volta.
    Por que fizemos isso: conseguir explicar com suas próprias palavras é o teste real de que você entendeu — decorar o comando sem entender o conceito não segura sob pressão num chamado de verdade.
    Cilada comum: escrever uma frase tecnicamente correta mas cheia de jargão que nem você mesmo reconhece de cabeça fria depois. Se soa complicado pra você, vai soar pior pra quem ler depois.
    🧑‍🏫 Aqui entra o Mentor (em breve): se sua frase ficou confusa até pra você mesmo, este é o ponto onde o chat com o Sênior-IA vai ajudar a refinar o entendimento.
  6. Ação: Confirme que nenhum dos quatro comandos exigiu senha ou alterou qualquer coisa no sistema.
    whoami id hostnamectl uname -a
    🔍 Detalhar cada comando desse bloco (reexecução)
    whoami
    Mostra só o nome (login) do usuário da sessão atual.
    id
    Mostra UID, GID e a lista completa de grupos do usuário.
    hostnamectl
    Identifica hostname, sistema operacional, versão do kernel e arquitetura.
    uname -a
    Mostra informações do kernel (nome, hostname, versão, build, arquitetura) — não mostra a distribuição.
    Resultado esperado: todos são comandos de leitura pura — se algum pediu senha de root, algo foi digitado errado.
    Por que fizemos isso: essa reexecução prova que investigar identidade não exige privilégio nenhum — é o tipo de checagem que você pode (e deve) fazer antes de qualquer decisão maior.
    Cilada comum: digitar sudo na frente "por hábito" de outros comandos. Nenhum dos quatro aqui precisa — se pediu senha, revise o que foi digitado.
  7. CENÁRIOAção: Remova o usuário de teste e prove que a máquina voltou ao estado anterior.
    sudo userdel -r teste-jr id teste-jr # deve falhar agora — e falhar aqui é o resultado certo grep teste-jr /etc/passwd || echo "removido com sucesso"
    🔍 Detalhar esse comando
    sudo
    Privilégio elevado, necessário para remover uma conta de usuário.
    userdel
    Remove uma conta de usuário existente.
    -r
    Remove também a pasta pessoal (home) e o mail spool do usuário — sem essa flag, os arquivos ficam órfãos no disco.
    teste-jr
    A conta a ser removida — a mesma criada no início da aula, fechando o ciclo sem deixar rastro.
    Resultado esperado: "no such user" no id e a mensagem "removido com sucesso". A máquina está exatamente como estava antes da aula.
    Por que fizemos isso: criar → observar → remover é o ciclo que permite estudar identidade sem deixar conta órfã em servidor. Conta esquecida é porta aberta: em auditoria, é um dos achados mais comuns.
    Cilada comum: esquecer o -r. Sem ele o usuário some, mas a pasta /home/teste-jr fica para trás ocupando espaço e confundindo o próximo técnico.
    Se o seu resultado foi diferente
    "userdel: user teste-jr is currently used by process" → algum shell ainda está aberto com esse usuário. Feche a sessão dele ou use sudo pkill -u teste-jr antes de repetir.

6. Antes de ver as opções — tenta responder

🧠 Recall ativo: quais são as quatro camadas de identidade que você deveria conferir antes de responder com certeza "quem eu sou e onde estou" num servidor Linux?
Usuário (whoami), UID/GID e grupos (id), host (hostnamectl), e kernel/arquitetura (uname -a). As quatro juntas é que dão certeza — uma sozinha pode enganar.

O chamado pedia acesso ao servidor srv02 pra investigar um problema de disco. Você roda hostnamectl logo depois de conectar:

$ hostnamectl
   Static hostname: srv01
O que essa evidência indica, e qual é a ação correta agora?
💡 Analogia do Sênior para Fixar: Executar 'hostnamectl' em produção é como conferir a placa do carro antes de dar a partida: garante que você não está no servidor de produção achando que está no de testes.
QUESTÃO 3 de 3 — detalhe que confunde todo iniciante

7.2 Kernel não é a mesma coisa que distribuição

Você rodou uname -a e viu Linux srv01 6.1.0-21-amd64 ... GNU/Linux. Seu colega pergunta: "então esse servidor é Debian, certo?"

uname -a mostra a versão do kernel. Isso já é suficiente pra dizer com certeza qual distribuição Linux está instalada?
💡 Analogia do Sênior para Fixar: Diferenciar o kernel Linux da distribuição é como diferenciar o motor do veículo da marca da carroceria: o mesmo motor 2.0 pode equipar modelos e marcas de carros completamente diferentes.

8. Procedimento profissional

  1. No início de todo chamado, rode whoami, id, hostnamectl e uname -a, nessa ordem.
  2. Compare o hostname com o que o chamado pediu — pare se não bater.
  3. Confirme UID e grupos antes de assumir qualquer coisa sobre seu próprio privilégio.
  4. Nunca confunda pertencer a um grupo com ter aquele privilégio ativo na sessão atual.
  5. Anote as quatro informações no registro do chamado, mesmo que pareçam óbvias.

Prevenção — o que evita repetir esse tipo de problema

Padronize as quatro checagens de identidade como primeiro passo obrigatório de qualquer chamado, antes até de ler o resto do ticket — vira reflexo, não decisão consciente cada vez. Documente no onboarding do time que "estar em produção" e "ser root" são coisas diferentes, pra ninguém repetir a confusão do colega desta aula.

9. Validação e encerramento

  • Você sabe, sem checar de novo, quais são as quatro camadas de identidade.
  • Você diferencia claramente estar no grupo sudo de estar como root agora.
  • Você sabe que uname mostra kernel, não distribuição.
  • Nenhuma alteração foi feita no sistema durante o laboratório.

Rollback e limites

Como toda a aula de hoje é somente leitura, não há rollback técnico. Se em algum momento um comando pedir senha de root sem você esperar, pare e confira o que foi digitado antes de continuar.
💡 Sobre repetição espaçada: "grupo sudo não é o mesmo que ser root" apareceu no Dia 1 e reaparece hoje, reforçado — essa repetição entre dias diferentes é proposital, é assim que a fluência gruda. O Anki vai juntar os dois cards.
