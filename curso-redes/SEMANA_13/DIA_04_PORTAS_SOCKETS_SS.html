2. Hoje aparecem dois sinais diferentes de falha ao testar uma porta. Ontem você já viu um deles — qual?
1. Se a porta da aplicação está aberta e o serviço está de pé — ping só confirma a camada de rede (ICMP), nunca a camada de transporte ou aplicação.
2. "Connection refused" — quando o host responde mas ninguém está escutando naquela porta (foi o caso de ontem, com o nginx parado). Hoje você compara isso com um segundo sinal, o timeout, que conta uma história diferente: alguém no caminho está bloqueando, sem nem responder.
🔗 Conecta com ontem: Ontem você separou o teste de porta como uma camada própria. Hoje você aprofunda: o que exatamente é um socket, e por que "connection refused" e "timeout" — dois erros que parecem parecidos — na verdade apontam pra causas completamente diferentes.
🔓 Privilégio de hoje: ler o SIGNIFICADO de um erro de conexão, não só o erro em si. Você ganha a distinção central: refused significa "alguém respondeu dizendo que não há serviço ali"; timeout significa "ninguém respondeu, o caminho pode estar bloqueado". São diagnósticos opostos.

2. O sênior te conta

Semana passada, outro ticket Uma aplicação nova numa porta 8080 não conectava remotamente, e o colega de plantão sugeriu desligar o firewall inteiro "só pra confirmar rápido" — em produção, com dezenas de outros serviços expostos por trás daquele mesmo firewall. Eu pedi 30 segundos: ss -tlnp mostrou o processo escutando na 8080 normalmente. O teste remoto com nc -zv dava timeout, não refused — sinal diferente, causa diferente. Fui direto no nft list chain inet filter input: policy drop, com regra só pra porta 22. Faltava uma linha: tcp dport 8080 accept. Adicionei, testei, resolvido — sem nunca desligar a proteção das outras 40 portas do servidor.

O ponto que fica: refused e timeout parecem "a mesma coisa não conectou", mas são sinais opostos — um é rejeição ativa, o outro é silêncio (bloqueio ou rota quebrada). Ler esse sinal antes de agir é o que evita a "solução" de desligar tudo pra testar.

$ nc -zv 192.168.10.50 8080

--- verificando o firewall no servidor ---
$ sudo nft list chain inet filter input
table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;
    tcp dport 22 accept
  }
}
→ Serviço OK, regra faltando. Não há regra para tcp dport 8080 accept.

5. Laboratório guiado — marca conforme for testando

🖥️ Testar este laboratório agora, num terminal Linux real (Killercoda) →
Segurança: execute os testes apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. Ação: inicie um serviço simples numa porta e confirme localmente.
    $ python3 -m http.server 8080 & $ ss -tlnp | grep ':8080'
    🔍 Detalhar esse comando
    python3 -m http.server 8080 &
    Sobe um servidor HTTP simples na porta 8080, em segundo plano, só para ter um serviço real escutando durante o laboratório.
    ss -tlnp | grep ':8080'
    Confirma localmente que a porta 8080 está em LISTEN, com o processo associado — a linha de base antes do teste remoto.
    Resultado esperado: porta 8080 aparecendo em LISTEN, com o processo associado.
    Por quê: confirmar localmente primeiro dá a linha de base — sem isso, você não sabe se um teste remoto que falha é do serviço ou do caminho.
    Cilada comum: esquecer de derrubar o servidor de teste no final — ele fica rodando e ocupando a porta pra próxima vez.
    Se o seu resultado foi diferente
    ss -tlnp não mostra o processo (coluna vazia) → sem sudo, o ss não tem permissão de ver o dono de sockets de outros usuários. Rode sudo ss -tlnp | grep ':8080'.
  2. Ação: de outra VM, teste a porta correta e uma porta sem serviço.
    $ nc -zv 192.168.10.X 8080 $ nc -zv 192.168.10.X 9999
    🔍 Detalhar esse comando
    nc -zv
    Testa se uma porta TCP aceita conexão, em modo zero-I/O (-z) e verboso (-v) — revisado no Dia 3.
    192.168.10.X 8080
    Porta com serviço real escutando — deve responder succeeded.
    192.168.10.X 9999
    Porta sem nenhum serviço — deve responder connection refused, o contraste que fixa a diferença entre refused e timeout.
    Resultado esperado: succeeded na porta certa, connection refused na porta sem serviço.
    Por quê: ver os dois sinais lado a lado (succeeded vs refused) é o que fixa a diferença antes de introduzir o terceiro sinal (timeout).
    Cilada comum: testar só uma porta e não comparar — sem o contraste, "refused" e "timeout" continuam parecendo a mesma coisa.
  3. Ação: adicione uma regra de firewall com policy drop, sem accept pra porta do serviço.
    $ sudo nft add rule inet filter input tcp dport 8080 drop $ nc -zv 192.168.10.X 8080
    🔍 Detalhar esses comandos
    nft add rule
    Adiciona uma nova regra a uma chain existente do nftables — o firewall padrão em distros Linux modernas.
    inet filter input
    Localização da regra: table inet (cobre IPv4 e IPv6), chain filter, hook input (tráfego destinado à própria máquina).
    tcp dport 8080
    Condição da regra: só afeta pacotes TCP com porta de destino (destination port) 8080.
    drop
    Ação: descarta o pacote silenciosamente, sem responder nada ao remetente — é isso que produz o sintoma de timeout, diferente de um reject que responderia com recusa explícita.
    nc -zv ... 8080
    Testa a porta 8080 especificamente (revisado no Dia 3) — aqui usado pra confirmar, na prática, que o drop vira timeout.
    Resultado esperado: timeout, em vez de refused ou succeeded.
    Por quê: reproduzir o timeout de propósito é o que prova, na prática, que ele vem do firewall — não é só teoria.
    Cilada comum: testar uma regra de drop na porta SSH por engano, numa VM sem console alternativo — isso te tranca fora da própria VM.
    🧑‍🏫 Aqui entra o Mentor (em breve): se você acidentalmente bloquear sua própria porta SSH ao testar firewall, este é o ponto onde o chat com o Sênior-IA vai ajudar a recuperar o acesso via console.
    Se o seu resultado foi diferente
    A regra de drop bloqueou a própria sessão SSH usada pra testar, e a sessão travou → clássico de nftables: sempre confirme que a regra de drop está restrita à porta de teste (8080), nunca aplique uma drop genérica de input numa sessão SSH ativa sem antes garantir uma regra explícita liberando a porta 22.
    "Error: Could not process rule: No such file or directory" → a table/chain inet filter ainda não existe nessa VM. Crie primeiro com sudo nft add table inet filter e sudo nft add chain inet filter input { type filter hook input priority 0 \; }.
  4. Ação: adicione a regra específica de accept e confirme que o teste remoto volta a funcionar.
    $ sudo nft add rule inet filter input tcp dport 8080 accept $ nc -zv 192.168.10.X 8080
    🔍 Detalhar esse comando
    nft add rule inet filter input
    Adiciona uma regra à chain input da table inet filter.
    tcp dport 8080 accept
    Libera especificamente o tráfego TCP com porta de destino 8080 — a regra que faltava para a porta responder de fora.
    nc -zv ... 8080
    Reteste da mesma porta, agora esperando succeeded após a regra ser adicionada.
    Resultado esperado: nc succeeded após a regra correta ser adicionada.
    Por quê: a regra específica corrige só a causa identificada — nunca precisou desligar o firewall inteiro em nenhum momento do laboratório.
    Cilada comum: adicionar a regra accept sem remover a regra drop anterior — dependendo da ordem, a primeira regra que casar decide, então a posição importa.
  5. Ação: documente o diagnóstico completo.
    # serviço: escutando (ss confirmou) # sinal remoto: timeout (não refused) # causa: firewall policy drop sem regra accept # correção: tcp dport 8080 accept
    Resultado esperado: checklist completo do diagnóstico — reproduzindo o painel 6 da prancha de hoje.
    Por quê: registrar o sinal exato observado (não só "resolvido") é o que ensina você a reconhecer o padrão refused-vs-timeout da próxima vez.
    Cilada comum: anotar "adicionei regra de firewall" sem registrar qual porta e qual sinal motivou — a próxima pessoa (ou você, meses depois) não vai entender o raciocínio.

6. Antes de ver as opções — tenta responder

🧠 Recall ativo: qual é a diferença de causa entre um erro "connection refused" e um "timeout" ao tentar se conectar numa porta?
Connection refused significa que o pacote chegou até o host, mas ninguém está escutando naquela porta — resposta ativa de rejeição. Um timeout significa que nenhuma resposta chegou — o caminho pode estar bloqueado por firewall, ou a rota está quebrada. São causas opostas, apesar de os dois parecerem só "não conectou".

8. Procedimento profissional

  1. Ao ver uma conexão falhar, leia o sinal exato — refused ou timeout — antes de qualquer ação.
  2. Confirme localmente com ss -tlnp se o serviço realmente está escutando.
  3. Se estiver escutando mas o teste remoto der timeout, verifique regras de firewall.
  4. Adicione a regra específica necessária — nunca desligue o firewall inteiro pra "testar".
  5. Documente serviço, sinal observado, causa e regra aplicada.

Prevenção

Nunca desligue um firewall inteiro em produção "só pra testar" — mesmo com pressa. Padronize o diagnóstico refused-vs-timeout como primeiro passo de qualquer chamado de conexão recusada: o sinal já diz onde procurar antes de qualquer regra ser tocada.

9. Validação e encerramento

  • O sinal de erro (refused vs timeout) foi lido corretamente antes de qualquer ação.
  • ss -tlnp confirmou o estado real do serviço localmente.
  • A causa foi confirmada como firewall antes de qualquer regra ser alterada.
  • Uma regra específica foi adicionada, sem desligar o firewall inteiro.

Rollback e limites

Adicionar uma regra de firewall é reversível removendo a mesma regra depois, se necessário. Nunca desligue o firewall inteiro "só pra testar" em produção — isso expõe todas as portas, não só a que você está investigando, criando um risco desproporcional ao problema.
