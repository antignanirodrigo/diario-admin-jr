2. Antes de ver as opções — tenta responder

🧠 Recall ativo: se o ping pro IP do túnel funciona (10.99.0.1 ↔ 10.99.0.2) mas o ping pra um IP dentro da rede interna do outro lado (10.10.10.50) não funciona, o que isso já elimina como causa, e o que ainda precisa ser verificado?
Isso elimina qualquer problema de handshake, chave ou Endpoint — a autenticação entre os dois peers está funcionando, prova disso é o ping direto entre os IPs do túnel ter sucesso. O que ainda precisa ser verificado é o caminho DEPOIS do túnel: o AllowedIPs do lado do Site A inclui 10.10.10.0/24? O servidor do Site A tem ip_forward habilitado pra rotear entre a rede do túnel e a rede interna? Existe uma rota de volta configurada na rede interna pra saber como responder pro IP do túnel?

6. Procedimento profissional

  1. Confirme o plano de controle primeiro: wg show mostrando latest handshake recente nos dois lados.
  2. Teste o túnel isoladamente: ping entre os IPs do próprio túnel (Address de cada lado).
  3. Se o túnel em si funciona mas a rede interna não responde, confirme AllowedIPs cobrindo a sub-rede de destino.
  4. Confirme net.ipv4.ip_forward = 1 no servidor que faz a ponte entre wg0 e a rede interna.
  5. Confirme que a rede interna sabe rotear a resposta de volta pro IP do túnel.

7. Laboratório guiado — marca conforme for testando

Segurança: execute os testes apenas em VMs descartáveis e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. No túnel montado nos dias anteriores, confirme wg show com latest handshake recente nos dois lados.
    Resultado esperado: handshake de poucos segundos ou minutos atrás.
  2. Simule uma terceira VM representando uma rede interna atrás do servidor, e tente pingá-la a partir do lado cliente.
    Resultado esperado: ping falha inicialmente, mesmo com o túnel funcionando.
    🧑‍🏫 Aqui entra o Mentor (em breve): se você não souber por onde começar a investigar, este é o ponto onde o chat com o Sênior-IA vai te guiar pela separação plano de controle / plano de dados.
  3. Verifique sysctl net.ipv4.ip_forward no servidor que faz a ponte.
    Resultado esperado: valor 0 antes da correção.
  4. Habilite com sysctl -w net.ipv4.ip_forward=1 e teste o ping de novo.
    Resultado esperado: ping pra rede interna funciona agora, 0% de perda.
  5. Documente a diferença entre os três testes: ping do túnel, ping da rede interna antes e depois do forwarding.
    Resultado esperado: relatório mostrando claramente onde o plano de controle terminava e o plano de dados começava a falhar.

8. Validação e encerramento

  • Handshake recente confirma só o plano de controle — não é prova de entrega de dados.
  • Ping entre IPs do túnel isola o problema: se funciona, o túnel em si está saudável.
  • ip_forward, AllowedIPs e rota de volta são os três itens do plano de dados a verificar em sequência.
  • Cada camada tem seu próprio teste — nenhuma prova a outra.

Rollback e limites

Habilitar ip_forward temporariamente com sysctl -w é reversível com um reboot ou com sysctl -w net.ipv4.ip_forward=0. Pra manter permanente entre reboots, seria necessário editar /etc/sysctl.conf — mudança que precisa ser documentada, já que transforma o servidor num roteador entre duas redes de forma persistente.
💡 Sobre repetição espaçada: "separar plano de controle de plano de dados" é um padrão de diagnóstico que você vai reusar em qualquer protocolo com handshake — não é exclusivo de WireGuard.
