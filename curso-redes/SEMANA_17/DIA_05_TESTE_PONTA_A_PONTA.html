1. Ontem você comparou regras de NAT e firewall valor por valor pra achar a causa real. Sem olhar: por que comparar "de memória" é um erro nesse tipo de diagnóstico?
2. Hoje o erro é diferente: testar de DENTRO da rede e concluir que o port forward funciona. O que esse teste de dentro realmente não prova?
1. Porque regras de NAT e firewall têm valores exatos (portas, IPs) que precisam ser lidos, não lembrados — um erro de "achismo" pode levar a corrigir a regra errada.
2. Não prova que o port forward funciona de fora — acessar o IP PRIVADO direto da LAN bypassa completamente o NAT, não passa pela regra DNAT nem pela chain forward. É uma conclusão falsa clássica.
🔗 Conecta com a semana inteira: Você já sabe configurar NAT, publicar serviço via DNAT, e diagnosticar entre NAT e firewall. Hoje fecha com o erro mais sutil de todos: testar de dentro da LAN e achar que provou o port forward — quando na verdade nem chegou perto de testar o caminho real.
🔓 Privilégio de hoje: validar pelo caminho que o usuário real usa. Você ganha a distinção entre testar de dentro (bypassa o NAT completamente) e testar de fora (atravessa NAT + forward de verdade) — e o caso especial do hairpin NAT, pra quando um cliente interno também precisa acessar via IP público.

2. Antes de ver as opções — tenta responder

🧠 Recall ativo: por que testar de dentro da LAN, acessando o IP privado direto, não prova nada sobre se o port forward funciona pra um cliente de fora?
Um cliente da LAN acessando 192.168.10.50 diretamente não passa pela cadeia NAT + forward nenhuma vez — ele nem sabe que existe uma regra DNAT. "Se não passou pela regra, não testou a regra" — o único teste válido do port forward é de uma origem genuinamente EXTERNA, atravessando o caminho publicado de verdade.

💡 Analogia do Sênior para Fixar: Aplicar as boas práticas de 05 TESTE PONTA A PONTA é como o protocolo de segurança da aviação: elimina pontos únicos de falha e garante previsibilidade operacional.

6. Procedimento profissional

  1. Nunca considere um port forward validado só com teste de dentro da LAN.
  2. Teste de uma origem genuinamente externa, atravessando o caminho publicado real.
  3. Se um cliente interno precisar acessar via IP público, trate como caso separado (hairpin NAT).
  4. Sem origem externa disponível, confirme cada camada com evidência e documente a limitação.
  5. Registre o caminho testado (interno, externo, ou ambos) junto com o resultado.

7. Laboratório guiado — marca conforme for testando

Segurança: execute os testes apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. Com o port forward já configurado, teste de dentro da LAN acessando o IP privado direto.
    # from LAN client (teste inválido pro port forward) $ curl http://192.168.10.50 $ traceroute 192.168.10.50
    🔍 Detalhar esse comando
    curl http://192.168.10.50
    Acessa o serviço direto pelo IP privado interno — não passa pela regra DNAT nenhuma vez, então não prova nada sobre o port forward.
    traceroute 192.168.10.50
    Mostra o caminho de rede percorrido — aqui, um único salto direto ao destino, confirmando que o tráfego nunca saiu pra fora nem voltou pelo IP público.
    Resultado esperado: serviço responde (OK app-test), mas sem passar pelo NAT — traceroute mostra 1 salto direto.
    Por quê: confirma que o serviço em si está saudável, mas deixa claro que esse teste sozinho não valida o port forward — foi direto, não tocou no DNAT.
    Cilada comum: fechar o chamado de "porta publicada" só com esse teste — ele prova só que o serviço funciona, não que alguém de fora consegue alcançá-lo.
  2. De uma origem genuinamente externa (outra VM fora da rede, ou simulação equivalente), teste o IP público.
    # from external client $ curl http://203.0.113.5:8080
    Resultado esperado: serviço responde (OK app-test), agora sim atravessando DNAT + forward de verdade.
    Por quê: esse é o único teste que realmente prova o caminho publicado completo — IP público → DNAT → forward → destino.
    Cilada comum: testar de uma máquina que, sem perceber, ainda está na mesma LAN (ex: mesma VPN ou mesma rede virtual) — o teste parece "externo" mas na verdade não sai do perímetro.
  3. De um cliente interno, tente acessar o IP público (não o privado) e observe o comportamento.
    # caso especial: cliente interno acessando via IP público $ curl http://203.0.113.5:8080
    Resultado esperado: timeout (curl: (28) Connection timed out), a menos que hairpin NAT esteja configurado — comportamento esperado, não bug.
    Por quê: hairpin NAT (ou NAT reflection) é um caso especial que exige configuração própria — não invalida o port forward já validado com origem externa real.
    Cilada comum: ver esse timeout e achar que o port forward "quebrou" — é um cenário diferente do caminho normal de fora pra dentro, não uma prova de regressão.
    🧑‍🏫 Aqui entra o Mentor (em breve): se você precisar que clientes internos acessem via IP público, este é o ponto onde o chat com o Sênior-IA vai ajudar a configurar hairpin NAT especificamente.
  4. Compare os três resultados (interno, externo, hairpin) e documente qual caminho cada um representa.
    Resultado esperado: tabela clara diferenciando os três cenários testados.
    Por quê: registrar o caminho testado junto com o resultado evita que alguém depois confunda "o serviço responde" com "o port forward funciona" — são afirmações diferentes.
  5. Feche o chamado só com o teste externo real documentado — reproduzindo o painel 6 da prancha de hoje.
    Resultado esperado: checklist completo com evidências anexadas.
    Por quê: só o teste de origem genuinamente externa prova o caminho publicado real — é o único que deve fechar um chamado de "serviço publicado com sucesso".

8. Validação e encerramento

  • O port forward foi validado com origem genuinamente externa, não só teste interno.
  • O caso de hairpin NAT foi reconhecido como cenário separado, não como falha do forward.
  • Cada teste realizado foi documentado com o caminho exato que percorreu.
  • Nenhum chamado foi fechado com base num atalho de teste que não prova o caminho real.

Rollback e limites

Os testes de hoje (curl, traceroute) são de leitura, sem risco. O cuidado real é não confundir "o serviço responde" com "o port forward funciona" — são duas afirmações diferentes, e só a segunda importa pro chamado de publicação de serviço.
