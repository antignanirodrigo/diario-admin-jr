SSH Hardening: Segurança sem Caos

endureça o acesso sem quebrar a operação; segurança também precisa ser previsível

ANTES DE ALTERAR, OBSERVE. DEPOIS DE ALTERAR, VALIDE.

1. O chamado

"Vou desabilitar root e trocar a porta SSH ao mesmo tempo." Janela de mudança de segurança marcada, mas o risco anotado é real: usuários, scripts e monitoramento podem quebrar. Mudar tudo junto dificulta saber, se algo quebrar, QUAL das duas mudanças foi a causa.

💡 Passa o mouse nas palavras destacadas pra ver uma dica rápida — clica se quiser a explicação completa com analogia.

2. Antes de ver as opções — tenta responder

🧠 Recall ativo: por que PermitRootLogin no é hardening real, mas trocar a porta SSH sozinha não é?
PermitRootLogin no remove o alvo de maior valor (root direto) — exige usuário nomeado + sudo, reduzindo o dano de uma credencial comprometida. Trocar a porta é só obscuridade — não impede um ataque de verdade, e ainda quebra scripts e monitoramento configurados pra porta 22.

6. Procedimento profissional

  1. Priorize hardening real (PermitRootLogin no, PasswordAuthentication no) sobre obscuridade (porta).
  2. Edite a configuração com sudoedit e valide a sintaxe com sshd -t antes de reiniciar.
  3. Nunca feche a sessão de teste antes de confirmar login com usuário nomeado + sudo.
  4. Se uma mudança adicional (como porta) impacta outros sistemas, adie até coordenar com a equipe.
  5. Documente a decisão de mudança: o que foi mantido, o que foi adiado, e por quê.

7. Laboratório guiado — marca conforme for testando

Segurança: execute os testes apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. Em VM de laboratório, com uma sessão SSH já aberta como usuário nomeado, edite sshd_config com PermitRootLogin no.
    Resultado esperado: arquivo editado, sem erro de sintaxe visível ainda.
  2. Valide com sudo sshd -t antes de qualquer restart.
    Resultado esperado: sem saída de erro, confirmando sintaxe válida.
  3. Reinicie o sshd e, MANTENDO a sessão atual aberta, abra uma nova sessão de teste tentando login como root.
    Resultado esperado: "Permission denied" para root, confirmando o bloqueio.
    🧑‍🏫 Aqui entra o Mentor (em breve): se o login com usuário nomeado também falhar após a mudança, este é o ponto onde o chat com o Sênior-IA vai ajudar a reverter usando a sessão original ainda aberta.
  4. Teste login com o usuário nomeado e confirme acesso sudo com sudo -l.
    Resultado esperado: login bem-sucedido, sudo -l mostrando permissões corretas.
  5. Só então feche a sessão original, documentando: mantido, mantido, adiado — reproduzindo o painel 6 da prancha de hoje.
    Resultado esperado: registro de mudança claro com decisões justificadas.

8. Validação e encerramento

  • A sintaxe foi validada com sshd -t antes de qualquer restart.
  • A sessão de teste original permaneceu aberta até a validação completa.
  • Root bloqueado e usuário nomeado com sudo funcionando foram confirmados.
  • Uma mudança de maior impacto (porta) foi conscientemente adiada, não aplicada por impulso.

Rollback e limites

Se o restart do sshd causar problema, a sessão original ainda aberta é o caminho de reversão — editar de volta e reiniciar de novo. O cuidado real é nunca aplicar múltiplas mudanças de hardening ao mesmo tempo sem conseguir isolar qual delas causou um eventual problema.
