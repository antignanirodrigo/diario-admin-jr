Samba: Permissões Combinadas

read only = no permite escrever — mas não garante que o arquivo criado seja legível por outra pessoa

2. Antes de ver as opções — tenta responder

🧠 Recall ativo: por que "read only = no" garante que alguém CONSEGUE escrever, mas não garante nada sobre quem mais consegue LER o que foi escrito depois?
read only = no controla só se a OPERAÇÃO de escrita é permitida naquele compartilhamento — é uma permissão de nível Samba. Mas o arquivo, depois de criado, ainda tem uma permissão Unix própria gravada nele (como qualquer arquivo Linux) — e essa permissão é definida pelo create mask do Samba no momento da criação. Se o create mask for restritivo demais (como 0600, só o dono lê e escreve), NINGUÉM MAIS vai conseguir acessar aquele arquivo depois, mesmo estando no mesmo compartilhamento com read only = no.

5. Ferramentas e leitura da evidência

OpçãoControla
read onlySe a operação de escrita é permitida no compartilhamento (nível Samba).
create maskTeto de permissão aplicado a arquivos NOVOS criados via Samba.
directory maskTeto de permissão aplicado a pastas NOVAS criadas via Samba.
--- estado do chamado #2204 (sem create mask definido) ---
$ ls -l /dados/uploads/
-rw-------  1 joao joao  2048 Sep  1 15:00 arquivo_joao.jpg
                    ↑ só joao lê/escreve — maria fica de fora

--- correção no smb.conf ---
[uploads]
   path = /dados/uploads
   valid users = joao maria
   read only = no
   create mask = 0664
   directory mask = 0775

$ sudo systemctl reload smbd

--- novo arquivo criado depois da correção ---
$ ls -l /dados/uploads/
-rw-rw-r--  1 joao joao  1024 Sep  1 15:30 arquivo_novo.jpg
                    ↑ dono e grupo podem ler/escrever, outros só leem
                    ↑ maria (se no mesmo grupo) já consegue acessar

6. Procedimento profissional

  1. Diante de "consigo escrever mas outro usuário não consegue ler", suspeite de create mask restritivo.
  2. Confirme com ls -l a permissão real do arquivo problema no servidor.
  3. Adicione create mask e directory mask apropriados no bloco de compartilhamento.
  4. Reaplique com systemctl reload smbd, e teste criando um arquivo novo.
  5. Corrija manualmente (chmod ou find) arquivos antigos já afetados — create mask não é retroativo.

    echo teste > /tmp/teste.jpg smbclient //localhost/uploads -U joao -c "put /tmp/teste.jpg antes.jpg" ls -l /dados/uploads/antes.jpg sudo tee -a /etc/samba/smb.conf > /dev/null <<'EOF' create mask = 0664 directory mask = 0775 EOF sudo testparm -s sudo systemctl reload smbd smbclient //localhost/uploads -U joao -c "put /tmp/teste.jpg depois.jpg" ls -l /dados/uploads/depois.jpg
    🔍 Detalhar essas opções do smb.conf
    create mask = 0664
    Define o teto máximo de permissão Unix aplicado a ARQUIVOS NOVOS criados através deste compartilhamento — 0664 = rw-rw-r-- (dono e grupo leem/escrevem, outros só leem). É um teto: bits além dele nunca são concedidos, mesmo que o cliente peça mais.
    directory mask = 0775
    Mesma ideia do create mask, mas aplicada a PASTAS novas — 0775 = rwxrwxr-x. Pastas precisam do bit de execução (x) pra serem navegáveis; por isso o valor é diferente do create mask.
    Resultado esperado: antes.jpg aparece com permissão -rw------- (só joao acessa). depois.jpg, criado depois do create mask, aparece com -rw-rw-r-- — agora legível por outros.
    Por que fizemos isso: ver os dois arquivos lado a lado, criados no mesmo compartilhamento antes e depois da mudança, prova visualmente que create mask afeta só criação futura — exatamente o ponto que confunde todo iniciante nesse tema.
    Cilada comum: as linhas create mask/directory mask precisam ficar DENTRO do bloco [uploads], não soltas no fim do arquivo — colar com tee -a sem confirmar a posição pode fazer elas caírem fora do bloco certo se houver outro compartilhamento depois. Confirme com cat /etc/samba/smb.conf antes de recarregar.
    Se o seu resultado foi diferente
    depois.jpg saiu com a mesma permissão de antes.jpg → as linhas provavelmente caíram fora do bloco [uploads]. Edite o arquivo diretamente e confirme com testparm -s -v | grep -A5 uploads que create mask aparece associado ao [uploads] certo.

8. Validação e encerramento

  • read only controla se a escrita é permitida; create mask controla a permissão do arquivo resultante.
  • create mask e directory mask agem como teto no momento da criação, com prioridade sobre umask do sistema nesse contexto.
  • Arquivos já existentes não são corrigidos retroativamente por uma mudança de create mask.
  • ls -l no servidor é a evidência definitiva pra confirmar a permissão real de um arquivo.

Rollback e limites

Ajustar create mask/directory mask é reversível e testável com testparm antes de aplicar. O cuidado real é escolher a permissão certa pro contexto: 0664/0775 é razoável pra compartilhamento de equipe, mas pode ser permissivo demais (ou restritivo demais) dependendo de quem mais tem acesso àquele mesmo diretório fora do Samba.
💡 Sobre repetição espaçada: "a operação sendo permitida não garante o resultado ter a permissão certa depois" é o mesmo tipo de camada extra visto na Semana 21 (Dia 5, permissão Unix separada do export rw) — vale reforçar esse padrão de múltiplas camadas de permissão em qualquer serviço de arquivo.
