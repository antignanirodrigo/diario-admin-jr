DNS Conceitual

DNS não é mágica nem arquivo único — é uma cadeia de perguntas até a resposta autoritativa

ANTES DE ALTERAR, OBSERVE. DEPOIS DE ALTERAR, VALIDE.

1. O chamado

Você digita app.empresa.local no navegador e nada abre. "Será que o DNS é só um arquivo grande em algum servidor?" "Onde está esse arquivo?" "Quem responde minha pergunta?" — três perguntas legítimas de quem nunca viu o fluxo real. DNS não é um arquivo, é uma cadeia de perguntas em hierarquia.

💡 Passa o mouse nas palavras destacadas pra ver uma dica rápida — clica se quiser a explicação completa com analogia.

2. O sênior te conta

Semana passada, outro ticket Um dev novo passou uma hora tentando descobrir "onde está o arquivo do DNS" pra editar manualmente e corrigir um app que não abria — ele imaginava um arquivo texto gigante em algum lugar, tipo um `/etc/hosts` global da internet. Sentei com ele e rodei dig app.empresa.local A: a resposta veio do resolvedor local (192.168.10.10), com TTL 300. Perguntei: "isso é a fonte da verdade, ou uma cópia?" Ele não sabia. Rodei de novo, agora direto no autoritativo com dig @ns1.empresa.local app.empresa.local A — mesma resposta, mas essa sim era a fonte real. O resolvedor só guarda cópia temporária em cache.

O ponto que fica: não existe "o arquivo do DNS". Existe uma cadeia de perguntas — resolvedor, root, TLD, autoritativo — e cada uma responde de um jeito diferente. Confundir cache com fonte da verdade é o erro que volta amanhã, quando o tema for TTL.

4. Ferramentas e leitura da evidência

ComandoO que confirma
dig nome AResolve um nome para um endereço IPv4 (registro A).
dig nome CNAMEMostra se o nome é um apelido apontando para outro nome.
$ dig app.empresa.local A
; <<>> DiG 9.18.20 <<>> app.empresa.local A
;; ANSWER SECTION:
app.empresa.local.   300  IN  A  192.168.10.50
;; SERVER: 192.168.10.10#53(192.168.10.10)

$ dig www.empresa.local CNAME
;; ANSWER SECTION:
www.empresa.local.   300  IN  CNAME  app.empresa.local.
;; SERVER: 192.168.10.10#53(192.168.10.10)

5. Laboratório guiado — marca conforme for testando

Segurança: execute os testes apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. Ação: consulte um domínio conhecido e leia a ANSWER SECTION completa.
    $ dig example.com A
    Resultado esperado: registro A com IP, TTL e servidor que respondeu.
    Por quê: ler os três campos (IP, TTL, servidor) juntos é o que ensina a diferenciar resposta de cache de resposta fresca.
    Cilada comum: ler só o IP e ignorar a linha SERVER — sem ela você não sabe se a resposta veio do resolvedor local ou de um servidor autoritativo.
  2. Ação: configure um servidor DNS local simples com uma zona de teste, se disponível.
    # exemplo com dnsmasq: adicionar em /etc/dnsmasq.conf address=/app.empresa.local/192.168.10.50
    Resultado esperado: zona respondendo a consultas locais.
    Por quê: montar sua própria zona de teste é o que transforma o conceito de "servidor autoritativo" em algo concreto que você controla.
    Cilada comum: esquecer de reiniciar o serviço dnsmasq depois de editar a config — a mudança não entra em vigor sozinha.
  3. Ação: adicione um CNAME apontando para o registro A e teste com dig.
    $ dig www.empresa.local CNAME $ dig www.empresa.local A
    Resultado esperado: dig mostra o CNAME e, seguindo a cadeia, o IP final.
    Por quê: ver o resolvedor seguir o apelido até o IP final, na prática, fixa a diferença entre CNAME (aponta pra nome) e A (aponta pra IP).
    Cilada comum: criar um CNAME apontando pra outro CNAME em cadeia longa — funciona, mas complica o diagnóstico e é evitado em produção.
    🧑‍🏫 Aqui entra o Mentor (em breve): se a resolução do CNAME não completar, este é o ponto onde o chat com o Sênior-IA vai ajudar a verificar a configuração da zona.
  4. Ação: compare o campo SERVER entre uma consulta ao resolvedor local e uma direta ao autoritativo.
    $ dig app.empresa.local A $ dig @192.168.10.20 app.empresa.local A
    Resultado esperado: ambos retornam a mesma resposta, mas de fontes diferentes.
    Por quê: essa comparação lado a lado é o que prova, na prática, a diferença entre cache e fonte da verdade — não é só teoria.
    Cilada comum: assumir que a resposta do resolvedor local está sempre atualizada só porque bate com o autoritativo agora — o cache pode ficar desatualizado depois de uma mudança recente.
  5. Ação: documente o fluxo completo observado.
    # resolvedor: 192.168.10.10 (cache) # autoritativo: 192.168.10.20 (fonte real) # A: app.empresa.local → 192.168.10.50 (TTL 300) # CNAME: www.empresa.local → app.empresa.local
    Resultado esperado: resumo com resolvedor, servidor, tipo de registro e TTL — reproduzindo o painel 6 da prancha de hoje.
    Por quê: esse resumo é o que você vai usar amanhã, quando o tema for TTL e cache — a base de hoje sustenta o diagnóstico de amanhã.
    Cilada comum: anotar só o IP final sem registrar de onde veio a resposta — sem isso, "o DNS está certo mas não funciona" vai parecer contraditório amanhã.

6. Antes de ver as opções — tenta responder

🧠 Recall ativo: quais são as quatro paradas que uma consulta DNS faz, do seu PC até a resposta final?
Cliente (seu PC) → resolvedor local → root (.) → TLD (.local, .com, etc.) → servidor autoritativo (que conhece a zona específica) → resposta volta pro cliente. Cada etapa é uma pergunta na cadeia, não uma consulta a um arquivo único.

QUESTÃO 2 de 3 — cenário de erro real

7.1 www.empresa.local é CNAME para app.empresa.local, que por sua vez tem um registro A

Um colega, vendo dois registros diferentes, acha que são consultas independentes sem relação.

Como o resolvedor realmente resolve www.empresa.local até chegar num IP?
💡 Analogia do Sênior para Fixar: A hierarquia DNS (Raiz . → TLD .br → Autoritativo) é a árvore genealógica postal: o servidor raiz aponta para o cartório do Brasil (.br), que aponta para o cartório da empresa.
QUESTÃO 3 de 3 — detalhe que confunde todo iniciante

7.2 "Se o resolvedor local responde rápido, isso significa que ele é sempre a fonte da verdade?"

Um colega acha que qualquer resposta rápida do resolvedor já é garantidamente atual.

Por que essa suposição pode estar errada?
💡 Analogia do Sênior para Fixar: Registros Tipo A apontam para endereços IPv4, enquanto registros CNAME são apelidos que apontam para outro nome canônico.

8. Procedimento profissional

  1. Ao investigar DNS, lembre que não existe um "arquivo único" — é uma cadeia hierárquica.
  2. Use dig nome A pra resolver o registro de endereço, e dig nome CNAME pra checar apelidos.
  3. Identifique qual servidor respondeu (linha SERVER na saída do dig).
  4. Diferencie o servidor autoritativo (fonte da verdade) do resolvedor local (repassa/cacheia).
  5. Ao seguir um CNAME, entenda que a resolução continua até achar um registro A final.

Prevenção

Sempre confirme a linha SERVER na saída do dig antes de tirar conclusão sobre um registro — nunca assuma que uma resposta rápida veio da fonte real. Isso evita horas de investigação num "arquivo DNS" que não existe.

9. Validação e encerramento

  • O fluxo hierárquico de resolução DNS foi entendido, sem tratá-lo como "um arquivo único".
  • A diferença entre registro A e CNAME foi confirmada na prática com dig.
  • O servidor autoritativo foi identificado como a fonte real da verdade.
  • Nenhuma configuração foi alterada só pra observar o fluxo.

Rollback e limites

dig é um comando de leitura, sem risco — não existe rollback necessário. O cuidado real é não confundir cache (resposta rápida do resolvedor) com fonte da verdade (servidor autoritativo), um erro que vai aparecer de novo amanhã com o tema de TTL.
