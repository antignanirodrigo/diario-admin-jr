2. O sênior te conta

Semana passada, outro ticket Um chamado dizia "DNS bugado, só um PC não resolve certo" e já vinha com sugestão de reconfigurar o servidor DNS inteiro. Testei os outros PCs da mesma sala: todos resolviam app.intra.example pro IP certo. Só o PC-02 insistia num IP antigo. Isso já descartava o DNS como culpado — se fosse o servidor, todo mundo veria o mesmo erro. Rodei grep '^hosts:' /etc/nsswitch.conf no PC-02: hosts: files dns. Ou seja, /etc/hosts é consultado antes do DNS. Abri o arquivo: uma entrada esquecida de meses atrás, de um teste antigo, apontando pro IP errado.

O ponto que fica: quando só uma máquina se comporta diferente das outras, o problema quase nunca é do serviço central (DNS) — é de algo local naquela máquina específica. Investigar o atalho local primeiro evita reconfigurar um servidor que nunca esteve errado.

ComandoO que confirma

5. Laboratório guiado — marca conforme for testando

Segurança: execute os testes apenas em VM descartável e confirme nomes de discos, hosts e arquivos antes de cada comando.
  1. Ação: adicione uma entrada errada em /etc/hosts para um nome que também existe no DNS.
    $ echo "192.168.10.99 app.intra.example" | sudo tee -a /etc/hosts
    Resultado esperado: resolução local criada, diferente do DNS real.
    Por quê: reproduzir a divergência de propósito é o que te deixa reconhecer o padrão da próxima vez que vir um caso real.
    Cilada comum: esquecer que essa entrada de teste fica lá depois do laboratório — sempre limpe /etc/hosts ao final.
  2. Ação: compare getent hosts com dig para o mesmo nome.
    $ getent hosts app.intra.example $ dig app.intra.example A +short
    🔍 Detalhar esse comando
    getent hosts
    Consulta o mecanismo de resolução de nomes COMPLETO do sistema — segue a ordem configurada em /etc/nsswitch.conf, incluindo /etc/hosts antes do DNS.
    dig ... +short
    Consulta o DNS DIRETO, ignorando /etc/hosts por completo — é uma ferramenta de diagnóstico de DNS, não do sistema de resolução geral.
    Resultado esperado: getent mostra o IP de /etc/hosts; dig mostra o IP real do DNS — divergentes.
    Por quê: essa comparação prova, na prática, que dig e getent hosts não consultam a mesma coisa — dig ignora /etc/hosts, getent segue a cadeia completa.
    Cilada comum: usar só dig pra diagnosticar um problema de resolução — ele nunca vai revelar um override em /etc/hosts, porque não consulta esse arquivo.
  3. Ação: confirme a ordem de resolução configurada.
    $ grep '^hosts:' /etc/nsswitch.conf
    Resultado esperado: hosts: files dns (ou ordem equivalente confirmando a prioridade local).
    Por quê: confirmar a ordem antes de agir evita assumir "files vem primeiro" quando, numa configuração não-padrão, pode ser o contrário.
    Cilada comum: assumir que todo sistema Linux tem a mesma ordem em nsswitch.conf — sempre confira, não presuma.
    🧑‍🏫 Aqui entra o Mentor (em breve): se a ordem estiver invertida (dns antes de files), este é o ponto onde o chat com o Sênior-IA vai ajudar a entender as implicações dessa configuração não-padrão.
    Se o seu resultado foi diferente
    Nenhuma linha retorna (grep vazio) → algumas distros usam uma sintaxe ligeiramente diferente; procure a seção inteira com cat /etc/nsswitch.conf | grep -A0 hosts ou abra o arquivo com um editor pra localizar a linha manualmente.
  4. Ação: faça backup, remova a entrada de teste e valide com getent hosts.
    $ sudo cp /etc/hosts /etc/hosts.bak $ sudo sed -i '/app.intra.example/d' /etc/hosts $ getent hosts app.intra.example
    Resultado esperado: getent hosts agora retorna o mesmo IP que o dig.
    Por quê: o backup antes de editar é o que te dá um caminho de volta imediato se a remoção afetar algo além da linha de teste.
    Cilada comum: remover a linha errada com sed sem antes confirmar com grep quais linhas seriam afetadas.
    Se o seu resultado foi diferente
    O sed removeu mais linhas do que deveria → restaure do backup imediatamente com sudo cp /etc/hosts.bak /etc/hosts e refaça o sed com um padrão mais específico (ex: incluindo o IP exato, não só o nome).
  5. Ação: documente a causa raiz correta.
    # DNS: sempre esteve correto (192.168.10.80) # causa real: entrada obsoleta em /etc/hosts local # ação: backup + remoção da linha + getent confirmou
    Resultado esperado: relatório curto confirmando a causa raiz correta — reproduzindo o painel 6 da prancha de hoje.
    Por quê: registrar "não era o DNS" explicitamente evita que a próxima pessoa reabra a investigação no lugar errado.
    Cilada comum: registrar só "corrigido" sem anotar onde estava o override — a mesma entrada esquecida pode reaparecer em outro PC clonado da mesma imagem.

6. Antes de ver as opções — tenta responder

🧠 Recall ativo: qual arquivo define a ORDEM em que o sistema consulta fontes de resolução de nomes, e o que normalmente vem primeiro?
/etc/nsswitch.conf define a ordem — tipicamente hosts: files dns, o que significa: primeiro /etc/hosts (files), só depois DNS. Se existe uma entrada em /etc/hosts, o DNS nem chega a ser consultado — o atalho local vence antes.

8. Procedimento profissional

  1. Quando só uma máquina, de várias, resolve diferente, suspeite de algo local primeiro.
  2. Confirme a ordem de resolução com grep '^hosts:' /etc/nsswitch.conf.
  3. Verifique /etc/hosts pra uma entrada que possa estar vencendo o DNS.
  4. Faça backup antes de editar, remova a entrada obsoleta, e teste com getent hosts.
  5. Confirme que a frota inteira agora resolve de forma consistente.

Prevenção

Inclua a checagem de /etc/hosts como primeiro passo padrão em qualquer chamado de "resolução inconsistente numa única máquina" — antes de sequer suspeitar do servidor DNS. Isso corta o tempo de diagnóstico de horas pra minutos.

9. Validação e encerramento

  • A investigação começou por /etc/hosts, não por reconfigurar o DNS que já estava certo.
  • A ordem de resolução foi confirmada via nsswitch.conf antes de qualquer conclusão.
  • Backup foi feito antes de editar /etc/hosts.
  • getent hosts confirmou a correção, refletindo o que uma aplicação real veria.

Rollback e limites

Com o backup (/etc/hosts.bak) feito antes da edição, reverter é simples: copiar o backup de volta. O cuidado real é não editar /etc/hosts sem antes confirmar exatamente qual linha é a obsoleta, evitando remover uma entrada válida por engano.
